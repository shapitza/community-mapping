# Backend architecture: Boundary-Control-Entity

The backend is organised **by business component**, not by technical layer.
Everything about one topic (for example places) lives in one package, and
inside it the code is split into three layers.

```
com.communitymap
├── organizations/     organizations and their registration
├── identity/          users and sign-in
├── members/           organization membership and roles
├── maps/              community maps
├── categories/        categories and their custom field definitions
├── places/            map items, observations, statuses, photos, links
├── activity/          activity log
└── platform/          cross-cutting things (health, error handling)

each component:
├── boundary/   what the outside world sees
├── control/    what the component does
└── entity/     what the component is about
```

## The three layers

| Layer      | Contains                                                         | Micronaut                                   |
| ---------- | ---------------------------------------------------------------- | ------------------------------------------- |
| `boundary` | HTTP endpoints, request and response records, mapping to entities | `@Controller`, `@Serdeable` records         |
| `control`  | Business rules, transactions, repositories                       | `@Singleton` services, `@JdbcRepository`    |
| `entity`   | Domain objects and enums                                         | `@MappedEntity`, enums                      |

A request flows **boundary → control → entity**:

```
POST /api/maps/1/items
  │
  ▼
places.boundary.MapItemController      validates MapItemRequest, calls request.toEntity()
  │
  ▼
places.control.MapItemService          sets map, author and timestamps, saves
  │
  ▼
places.control.MapItemRepository       SQL generated by Micronaut Data
  │
  ▼
places.entity.MapItem                  mapped to table map_item
```

## Rules

1. **entity** depends on nothing in `control` or `boundary`.
2. **control** never depends on `boundary`. The boundary turns a request into an
   entity (or plain values) before calling control, so control does not know
   HTTP or JSON exists.
3. **Another component's boundary is off limits.** Components talk to each other
   through `control`. For example, `places.control` will call
   `activity.control` to record that a place was added; it never calls an
   activity endpoint.
4. **No cycles between components.** If `places` uses `categories`, then
   `categories` must not use `places`.

These rules are checked on every build by
`backend/src/test/java/com/communitymap/ArchitectureTest.java` (ArchUnit).
Breaking one fails the build with a message naming the offending class.

## Where does a new class go?

| You are adding…                                   | Put it in                         |
| ------------------------------------------------- | --------------------------------- |
| A new endpoint                                    | `<component>.boundary`            |
| The JSON body of a request or response            | `<component>.boundary` (a record) |
| A rule like "only admins may delete members"      | `<component>.control`             |
| A database query                                  | `<component>.control` repository  |
| A new table                                       | `<component>.entity` + migration  |
| Something every component needs (error handling)  | `platform`                        |

If a class seems to belong to two components, that is usually a sign that one
of them should call the other's `control`, or that it is a component of its own.

## Why not layer packages?

With `controller/`, `service/`, `repository/` and `domain/`, a change to one
feature touches four folders, and nothing stops any class from calling any
other. With components, a feature lives in one place, and the rules above keep
the dependencies pointing one way. Further reading: Adam Bien,
"Boundary Control Entity" (https://bce.design).
